# Agent Factory: critical review (2026-10-21)

Reviewed against main `9604e60` (ADR-0043 PR 1 merged), the roadmap, the master plan and the Guestbook run.
Purpose: decide what the factory must prove next, from a product's launch to its end of life, before adding more.
A point-in-time review: the journey's current state is in [roadmap.md](roadmap.md).

## Verdict
The engine is well built and disciplined: deterministic routing, sealed evidence, a Level 3 gate, packs, a
work ledger. But **we have built far more control surface than proven journeys**. One product has been
delivered live, and it was never pushed, never iterated live, never run beyond deploy, never retired, and
its owner wasn't happy with it. Half a product's life (run, upkeep, rollback, end of life) barely exists.

Every idea added today (PR loop, skill upkeep, decision sheet, modules, chat per station, control plane)
is reasonable on its own. Together they repeat master plan risk #1, **breadth over depth**, at about 9 more
weeks of part-time work, while nothing new reaches a live, end-to-end, demonstrable journey.

Seven steps work live, nine are built but unproven, and seven are missing. Every missing step is at either
end of the product's life: the design conversation, or after delivery.

## What's strong (keep)
- A deterministic engine with agents inside stations; the engine judges, agents report evidence.
- Sealed evidence, change risk, the readiness gate and the quality pillars: the trust story is real.
- Stack packs: adding a stack is adding a folder.
- The work ledger: a good spine for the whole lifecycle (every finding, deferral and incident becomes an item).

## What's weak
1. **Proof lags features.** About 22,000 lines of engine code and 41 ADRs, against one live delivery.
   Builder presets, phase registries, org columns and capability grants serve organisations that don't
   use the factory yet.
2. **Product quality isn't measured.** Level 3 checks the repo, not the product. Nothing judges the UI,
   the design choices or whether a sensible person would ship it.
3. **The lifecycle is lopsided.** Plan → build → verify is deep; run → maintain → retire is close to empty.
   A software factory that stops at deploy is a code generator with good paperwork.
4. **Complexity is starting to cost.** `actions.py` 1,875 lines, `stations.py` 1,973, `pipeline.py` 1,136.
   Each change gets slower, and part-time solo work can't absorb that for long.
5. **Process drift.** The roadmap was rewritten three times today by parallel sessions, and items were lost
   twice. One session at a time should own the roadmap. (Resolved 2026-10-26 by moving the plan into the
   repo, where git turns concurrent edits into conflicts: see [README.md](README.md).)

## On today's questions
- **"Other" in the decision sheet:** yes. Cheap and right; the architect turns it into a concrete choice
  with consequences, and the engine still checks completeness.
- **Chat with the architect:** yes, but only at stations a person owns (design decisions, spec review, risk
  approval, assessment triage). This is the "discuss" mode already planned: one thread per station run,
  sealed with the evidence. Not in build, scan or deploy: there it invites people to argue with the checks.
- **Control plane, every station integrable:** yes, that's master plan principles 2 and 5, and the tool
  station contract already points there. Prove it with **one** real integration on the journey (GitHub:
  repo, PR, CI status) before adding more adapters.

## Recommendation
**Make the golden journey the north star.** Freeze new ADRs and new control surface until it runs live end
to end, once, on a demo-worthy product. Re-order the work into five milestones, each finished by a live run
recorded as evidence and a short demo.

| Milestone | Contents | ~Days |
|---|---|---|
| **J1. Launch, done well** | ADR-0043 PR 2 (e2e before deploy); trimmed ADR-0044: decision sheet with "Other" and architect chat, the v0 baseline, Tailwind + shadcn/ui, auth, authz and observability as modules; publish to GitHub live | ~7 |
| **J2. Iterate safely** | feedback → change live; rollback to the last good release; accepted/closed state | ~3 |
| **J3. Team repo** | live PR test; PR loop: CI back, comments continue the PR, merged closes | ~3 |
| **J4. Run and maintain** | a minimal Operate phase: watch health and error rate from `/metrics`, an alert opens an incident item in the ledger, "Make this change" fixes it; scheduled upkeep (dependency bumps and image rescans) | ~4 |
| **J5. End of life** | a retire flow: freeze changes, final sealed evidence, data export, undeploy, archive the product repo, a decommission record on Outcomes | ~2 |

About 19 days. After J5 the factory can show the whole life of a product, which is what sells the consulting
practice.

**Deferred until after J5:**
- skill upkeep (keep only the usage roll-up page, ~1 day, if it's wanted sooner);
- the full honeycomb set (rate limits, caching, flags, chart HPA/PDB) beyond what J1 needs;
- `react-spa`, full-stack and later packs;
- chat at every station; promotion environments (after the cluster target and the secret store).

**How to keep it honest:**
- One scripted **journey acceptance test** that runs the whole journey in dry-run in CI, so nothing that
  works today silently breaks.
- One **live run per milestone**, its sealed evidence kept as the demo record.
- One session owns the roadmap; other sessions propose changes in their handoff. (Replaced 2026-10-26 by
  the rules in [README.md](README.md).)
