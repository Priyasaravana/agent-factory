# Upgrading the factory

## The routine
```bash
make upgrade      # = make backup, git pull --ff-only, rebuild, wait for health, make sandbox-check
```
Then open the UI: the header should show **readiness ready** and **sandbox ready**.
If anything looks wrong, roll back (below).

## What protects an upgrade

| Layer | Catches | Where |
|---|---|---|
| Unit and contract tests | engine, auth and UI logic; OpenAPI drift | CI `engine`, `auth`, `web` |
| Golden path | the app template still verifies; the chart lints | CI `golden-path` |
| **Images** | every image builds; engine tests pass **on the Python inside the factory image**; the sandbox image verifies the golden path as the sandbox user, without interpreter downloads | CI `images` |
| **Whole stack** | `docker compose up` in dry-run; sandbox isolation from inside a real sandbox; a browser walks sign-in → readiness → product → delivered → feedback → archive | CI `e2e` (screenshots and logs kept as evidence) |
| Next Python | engine tests on 3.13 / 3.14, advisory | CI `engine-next-python` |
| Version rules | factory image = auth image = CI Python; the sandbox offers the Python the golden path pins | `engine/tests/test_python_versions.py` |
| Weekly run | base-image and upstream drift, even with no PRs | CI schedule |

## Dependabot pull requests
- **Patch and minor updates with all CI jobs green:** merge.
- **Major updates, and anything under `images/` or `web/Dockerfile`:** merge only when `images` and `e2e` are green. Read the changelog for breaking changes.
- **Python base images** get patch updates only (Dependabot is told to ignore minor and major bumps). Moving the factory to a new Python is one deliberate PR: the three images and CI together.
- **Apps get newer Python independently.** Add the version to `APP_PYTHONS` in `images/sandbox/Dockerfile`, then bump `.python-version` and the runtime image in the template (or in an app).
- **Recommended in GitHub:** protect `main` with required status checks (`engine`, `auth`, `web`, `golden-path`, `images`, `e2e`). Then "auto-merge" on a Dependabot PR waits for them.

## Backup and rollback
```bash
make backup                                              # safe while running; → backups/agent-factory-<timestamp>.tar.age
make restore BACKUP=backups/agent-factory-<ts>.tar.age   # stops the factory, keeps your current data aside
```
- **Backups are encrypted (S-17, 2026-11-19).** They hold the auth database, product repos and hidden
  scenarios, so `make backup` (and `make upgrade`, which takes one first) refuses to write one in clear.
  Once: `age-keygen -o ~/.agent-factory-backup.key` (macOS: `brew install age`), then set
  `BACKUP_AGE_RECIPIENT=<the public key, age1…>` and, for restores, `BACKUP_AGE_IDENTITY=~/.agent-factory-backup.key`
  in `.env`. Keep the key file somewhere other than this machine's `backups/` (a password manager); without
  it a backup can't be restored. `BACKUP_PLAINTEXT=1` writes an unencrypted folder, owner-readable only, if you
  knowingly want one. `make restore` also takes an older plaintext folder.
- **What a backup holds:**
  - a consistent SQLite snapshot of the factory database (products, changes, events, workflows, skills);
  - the auth database (users, token hashes, audit);
  - product repos, hidden scenarios, change worktrees and artifacts.

  Not included: the kind cluster and images inside dind; they are rebuilt or re-delivered.
- **Rolling back code:** `git checkout <previous commit>`, then `make up`. If that version's data format differs, restore the backup taken before the upgrade. `backups/<…>/factory-version.txt` records which commit a backup came from.
- **After a restore, incident response asks first.** `make restore` leaves a marker; until a reading has matched each
  product's recorded release with the live one, the factory proposes incident steps instead of taking them, and it
  never applies a release over a newer live one (ADR-0049 §4).
- **Changes are safe across upgrades.** Each change is pinned to a workflow version and its pinned skills. Interrupted changes are marked on restart and resumed by a person.

## Version notes
- **Tokens as files, and GitHub App tokens (S-06, 2026-11-25).** Tokens no longer need to sit in `.env`: `env://NAME` also reads the file `NAME_FILE` names, and compose mounts `.secrets/` read-only at `/run/secrets` in the factory. Your current `NAME=<value>` lines keep working. To move them: `make secrets-files` (it writes `.secrets/<name>` files, 0600, puts `NAME_FILE=/run/secrets/<name>` in `.env`, and keeps the old `.env` in `backups/`; on Linux also `sudo chown -R 10001 .secrets`), then `make upgrade`, check publishing and a PR still work, and delete the backup. Better still, a GitHub App: see `.env.example` ("GitHub App instead of long-lived tokens").
- **Images by digest, overrides included (S-07, 2026-11-25).** Every image compose pulls must now be pinned by digest, and `make up`, `make up-live`, `make upgrade` and `scripts/restore.sh` check that first (`scripts/pin-images.py --check-compose`, with your `.env` applied). `LITELLM_IMAGE` is retired: if your `.env` sets it, the check stops and says so. Set `LITELLM_REPO` (repository and tag) and `LITELLM_DIGEST` (`sha256:…`) instead, or remove it to use the pinned default. The images rebuild from pinned bases, and dind and postgres are recreated once.
- **Your config edits move to `config.local.yaml` (phase B, 2026-11-25).** `.agent-factory/config.yaml` is now only the shipped default; an install's own settings go in the gitignored `.agent-factory/config.local.yaml`, merged over it at start (mappings key by key, lists and values replaced; the factory's log names each setting it took from there). It is never built into an image: compose mounts `.agent-factory/` read-only, so an edit takes effect with `docker compose restart factory`. `make upgrade` now **refuses while `config.yaml` has local edits, staged or not**, so pulls stop colliding with them. Once, before upgrading: `make config-split` writes your edits as the override and proves the default plus the override loads exactly as your edited file; read it, then `git checkout -- .agent-factory/config.yaml` and `make upgrade`. If your file removed a setting the default has, it stops and names it (an override can't remove a key: set the value you want instead). See `.agent-factory/config.local.example.yaml`.
- **Security gates, cluster tools and headers (S-08, S-10, S-11; 2026-11-24).** `make upgrade` rebuilds the images with kind v0.33.0, kubectl v1.37.2 and helm v3.22.1 (the earlier versions carried fixable CRITICAL CVEs), each checked against its checksum. **The local cluster now runs Kubernetes 1.37** (`cluster/kind-config.yaml` pins the node image by digest): a running cluster keeps its version (1.32) until `make reset-cluster`, which recreates it and needs every product on it redeployed. kubectl 1.37 against a 1.32 cluster is outside Kubernetes' supported skew, so reset the cluster soon after upgrading, at a time when nothing is mid-test on it. The UI now sends security headers, including a Content-Security-Policy that refuses inline scripts: if a page of your own behind the gateway breaks, the browser console names what was refused. Sign-in allows a burst of 20 attempts per address, then 10 a minute (429). `make sandbox-check` also checks the headers.
- **Paths around the sandbox (ADR-0048, assessment findings S-02, S-03, S-04).** No reset. `make upgrade` restarts dind behind its new entrypoint (`cluster/dind-firewall.sh`; the kind cluster and images stay in its volume). **App addresses move** from `http://localhost:<port>` to `http://127.0.0.1:<port>`: products already delivered show the new address after the restart, and a `public_app_base_url: http://localhost` in your own `config.yaml` is served as 127.0.0.1 without editing it. Open the UI on `http://localhost:8080` (on 127.0.0.1 it sends you there). App namespaces on the local cluster get a NetworkPolicy at the first start after the upgrade (on a cluster target: at each app's next deploy, so redeploy those you want covered now): pods reach DNS and their own namespace only, and a chart that ships its own egress-allowing policy is refused; a blueprint whose apps must call something outside sets `app_egress: open`. A factory that more than one person uses **must** set `factory.shared: true` (nothing detects sharing yet), and then starts live only with the model gateway in api_key mode. Behind your own reverse proxy, pass the browser's `Host` through, or writes are refused as cross-site. `make sandbox-check` now also runs `scripts/sandbox-paths-probe.sh`.
- **Pod Security on app namespaces (assessment finding S-05; 2026-11-24).** No reset. Every deploy now labels the app's namespace for Kubernetes' Pod Security admission: `restricted` when the chart meets it (new products from fastapi-service 1.2.1 and nextjs-web 1.6.1), `baseline` for products made before, which keep deploying; the change's events say what restricted would refuse. A chart with a privileged pod, host namespaces, host paths, host ports or added capabilities is refused before it is installed. Apps already running on the local cluster get `baseline` at the first start after the upgrade (on a cluster target: at their next deploy). The factory never lowers a namespace from `restricted`; to do it deliberately, `kubectl label namespace <ns> --overwrite pod-security.kubernetes.io/enforce=baseline`.
- **Gateway proof (ADR-0012, assessment finding S-01).** No reset, nothing to configure: `make upgrade` rebuilds the images and `factory-init` makes the proof in two new volumes (`gateway-proof-engine`, `gateway-proof-web`). From then on the engine answers only requests that came through the gateway, so anything of your own that called `factory:8000` directly with `X-Auth-*` headers stops working: go through the UI port with an API token. Outside compose, `AUTH_MODE=gateway` now needs `GATEWAY_PROOF_FILE` (and your proxy must send its content as `X-Gateway-Proof`); `AUTH_MODE=off` is unchanged. `make sandbox-check` now also runs `scripts/gateway-check.sh`.
- **Repository sources (ADR-0047).** No reset, nothing required: the `existing_repos` token settings become the `default` source, bound to the host of `existing_repos.api_url` only (github.com unless you changed it). **If you allow more than one host**, repos on the others are read anonymously (public only) and can't get pull requests until you add a source for that host with its own token. Team repos onboarded before resolve to it (or to a source naming their owner) at their next change, recorded on the product. To give an org its own token, add a source on **Integrations → Repository sources** with a reference such as `env://REPO_ACME_TOKEN` (put the value in `.env` and restart once so the engine sees it), or under `existing_repos.sources` in `config.yaml`. Admin-made sources may only name references matching `existing_repos.source_token_refs` (default `env://REPO_*`). Clones now use the source's token when it resolves (private repos work); a token a public repo refuses falls back to reading it anonymously and says so.
- **Stack packs (ADR-0041, step 1).** No reset. The FastAPI golden path moved into a pack: `templates/fastapi-service/` is now `packs/fastapi-service/template/` and the `fastapi-golden-path` skill `packs/fastapi-service/skills/`. In a customised `config.yaml`, add `packs: [packs/fastapi-service]` and, on the `fastapi-service` blueprint, replace `template`, `verify_command` and `stack` with `pack: fastapi-service` (drop `service_port` and `chart_path` unless you mean to override the pack; overrides are recorded in each change's evidence). `phases.packs` is still read, as an alias of `packs:`. Published workflow versions that list `fastapi-golden-path` on an agent keep running (the skill is now preloaded from the product's pack instead); a draft made from one reports `uses unknown skill 'fastapi-golden-path'` until you remove it from the agent or go back to the factory default.
- **Lanes per kind of work (ADR-0039, step 1b-3a). Reset once more (data generation 4).** The single standard lane and its windows are replaced by four factory default lanes in `workflow-templates/standard/lanes/` (New product, Product change, Repo assessment, Repo change). In `config.yaml`, replace `workflows: {standard: …}` and `default_workflow` with the four lanes (see the shipped config) and add `use_factory_defaults: false`. Data from 1b-2 is refused at start: run `docker compose run --rm --no-deps --entrypoint agent-factory factory reset --confirm`, then `docker compose up -d`.
- **One workflow for the org (ADR-0037, step 1b-2). Reset once more.** Workflows no longer belong to a blueprint: the config lists them under `workflows:` (default `standard: workflow-templates/standard`) and every product runs `default_workflow`. Drop `workflow_template` from your blueprints. Data from 1b-1 (workflows named after blueprints) is refused at start: run `docker compose run --rm --no-deps --entrypoint agent-factory factory reset --confirm`, then `docker compose up -d`.
- **One standard lane (ADR-0037, step 1b-1). Your data is dropped.** The four templates (`default`, `api-security-review`, `assess`, `repo-change`) are replaced by `workflow-templates/standard` with a window per change kind (`presets.yaml`); the `existing-repo-change` workflow is gone (repo changes run the `repo-change` window of `existing-repo`). There is no migration: the factory refuses to start on older data and names the command. Take a backup, then run `docker compose exec -u factory factory agent-factory reset` to see what goes and `… reset --confirm` to drop products, changes, events, evaluations and workflows (members, skills and config stay); the next start seeds the standard lane. In a customised `config.yaml`, set `workflow_template: workflow-templates/standard` on every blueprint and drop `change_workflow_template`.
- **Model gateway (ADR-0036).** Nothing changes by default (`model_gateway.provider: direct`). `.env.example` gains `LITELLM_MASTER_KEY` and `MODEL_GATEWAY_DB_PASSWORD`; the config gains a commented `model_gateway:` section. To turn it on, see the runbook (*Route agents through the model gateway*). The sandbox's egress proxy is recreated on the next start when the gateway is on.
- **Scan stations named after their check (ADR-0035).** Re-draft **fastapi-service**, **existing-repo** and **existing-repo-change** from their templates again to get the *Secret / Code / Dependency / Config scan* stations and the `checker` agent. Versions already published keep their tool-named stations, which still run. To use Snyk or GitHub, see the runbook (*Use Snyk or GitHub for a check*).
- **Tool stations (ADR-0034).** Re-draft **fastapi-service**, **existing-repo** and **existing-repo-change** from their templates (Workflows → edit → *Start from a template* → *Use template* → *Publish*) to get the Semgrep, OSV-Scanner, gitleaks and Trivy stations. The first run pulls the tool images into dind.
- **Pull requests to existing repos (ADR-0033).** `config.yaml` gains `change_workflow_template` on `existing-repo`, `existing_repos.write_token_ref` and `registry.npmjs.org` in `sandbox.egress`; add `REPO_GITHUB_TOKEN` to `.env`. The sandbox image now includes Node.js and is rebuilt on first start.
- **Existing repos (ADR-0031).** `.agent-factory/config.yaml` gains the `existing-repo` blueprint and an `existing_repos:` section; merge them into a customised config. Its workflow is seeded on first start.
- **Work items (ADR-0030).** Nothing to do: changes from before read as `new` (first iteration) or `feature`, products as target `new`.
- **New names.** Upgrading to the Product/Change/Blueprint names (ADR-0029) renames the database tables in place on first start; `product_lines:` and the old limit names in config still load.
- **No root in the factory's containers (ADR-0018).** Nothing to do:
  - `make upgrade` (or `make up`) adds the one-shot `factory-init` step. It hands
    `/data` and dind's client certs to uid 10001, which also fixes files earlier
    root CLI calls left behind.
  - The web gateway now listens on 8080 inside its container. The host URL
    stays `http://localhost:8080`.
  - Afterwards, `make privilege-check` should report `least privilege: OK`.
